# ADR-0001: Целевая архитектура — квартет Bugget.{Api,Application,Domain,Infrastructure} + Contracts

- **Статус:** Accepted
- **Дата:** 2026-07-26
- **Решение принял:** владелец продукта

## Контекст

Бекенд — 29 проектов, ~39k строк C#. Граф проектов уже ациклический, но слоение
классическое трёхзвенное, а не Clean:

```
Bugget (Api) → Bugget.ExternalClients → Bugget.BO → Bugget.DA → Bugget.Entities
Users.Api → Users.BO → Users.DA → Users.Entities
```

Из этого следуют три конкретные проблемы:

- `Bugget.BO` — слой бизнес-логики — ссылается на `Bugget.DA`, а тот тянет Npgsql и Dapper.
  То есть бизнес-логика транзитивно зависит от драйвера БД.
- Все 16 портов `I*DbClient` объявлены **внутри** `Bugget.DA`. Это интерфейсы внутри
  инфраструктуры, а не инверсия зависимости: бизнес-слой не владеет своими контрактами.
- `Bugget.Entities` смешивает `DbModels`, `DTO`, `Views` и `BO` в одном проекте.
  Доменной модели как отдельной сущности нет.

Плюс россыпь мелких библиотек (`Monade`, `Flow`, `Caching.Local`, `TaskQueue`,
`Authentication`, `BugReport.Logging`, `OidcAuth`, `FakeAuth`, `MattermostOAuth`),
каждая из которых — отдельный csproj ради нескольких сотен строк.

Три модуля (`Bugget.*`, `Users.*`, `Authorization.*`) уже живут в одном процессе `app-api`;
nginx только маршрутизирует по префиксу.

## Решение

Целевая раскладка бекенда — один квартет плюс контракты:

```
Bugget.Api ──────────► Bugget.Application ──────► Bugget.Domain
    │                        ▲
    │                        │  (порты объявлены здесь)
    └──► Bugget.Infrastructure┘        Bugget.Contracts (без зависимостей)
         (подключается только DI-композицией из Api)
```

- `Bugget.Domain` и `Bugget.Application` не зависят от persistence, транспорта, ASP.NET,
  HTTP-клиентов и внешних драйверов.
- Порты (`I*DbClient` и прочие) объявляются в `Application`; `Infrastructure` их реализует.
  Направление зависимости — `Infrastructure → Application`.
- `Api` знает про `Application` и про `Infrastructure`, но вторую — только чтобы собрать DI.
- `Users.*`, `Authorization.*` и вспомогательные библиотеки растворяются в квартете.
  Это компайл-тайм реструктуризация, а не удаление функциональности.
- Граф проектов обязан остаться DAG.

**Чем это не является.** URL-пути публичного API сохраняются 1:1 — все три модуля и так
в одном процессе, внешние маршруты снимает nginx, и деплой от слияния не меняется.
Схема БД не меняется. `/_internal/auth` неприкосновенен: его дёргает сам nginx через
`auth_request`.

## Последствия

- Бизнес-логику можно тестировать без Postgres и без ASP.NET — это предпосылка
  для юнит-тестов, которых сейчас мало.
- Дифф миграции огромный по строкам и почти нулевой по логике: это перемещения файлов.
  Значит, порядок обязателен — сначала сеть безопасности (characterization-тесты
  публичного контракта и интеграционные тесты в CI), потом перемещения.
- Правило слоёв принуждается архитектурными тестами (NetArchTest), а не ревью. До миграции
  тесты фиксируют текущий граф («хуже не станет»), после — переписываются на целевой.
- git blame по перемещённым файлам портится, открытые ветки конфликтуют. Поэтому слияние
  идёт отдельным PR без функциональных правок.

## Отброшенные альтернативы

- **Оставить трёхзвенку, добавить только гейты.** Дёшево, но не убирает зависимость
  бизнес-логики от драйвера БД — то есть не решает исходную проблему.
- **Квартет на каждый модуль (modular monolith: `Bugget.*` + `Users.*` + `Authorization.*`).**
  Владелец хочет, чтобы `Users` и `Authorization` исчезли как отдельные единицы; три
  квартета вместо одного — это тот же зоопарк проектов под другим именем.
- **Architecture-first: сначала перекладываем слои, потом строим harness.** Самый
  рискованный рефакторинг делался бы без сети безопасности на проде у заказчика.
  Порядок выбран обратный — см. ADR-0002.
