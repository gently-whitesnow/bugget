# ADR-0003: DDD обязателен для нового кода, легаси мигрируем только при касании

- **Статус:** Accepted
- **Дата:** 2026-07-26
- **Решение принял:** владелец продукта

## Контекст

Модель сейчас анемичная: типы в `Bugget.Entities/BO` — это DTO-подобные контейнеры
свойств, вся логика лежит в сервисах `Bugget.BO/Services`. Инварианты репорта (фазы
Test/Fix, переходы, участники, regression-циклы) не выражены в типах и держатся
на дисциплине вызывающего кода.

Владелец сознательно **не** заказывает полный переход на rich-модель: переписывать
39k строк ради формы — дорого и рискованно на проде у заказчика. Но и продолжать
писать новые фичи анемично — значит увеличивать тот же долг.

Ключевой факт: без записанного решения это требование нечем принудить. Агент, который
пишет фичу, реконструирует стиль из соседнего кода — а соседний код анемичный.

## Решение

**Новый код пишется по DDD.** Новая фича или новый агрегат — это rich-модель:
поведение и инварианты живут в доменном типе, а не в сервисе-процедуре.

- Агрегат владеет своими инвариантами: невалидное состояние недостижимо через публичный API типа.
- Сервис `Application` оркеструет — загрузить агрегат, вызвать его метод, сохранить.
  Он не принимает решений за домен.
- Доменные типы не зависят от persistence, транспорта и ASP.NET (см. ADR-0001).

**Легаси мигрируется только при касании.** Правишь анемичный кусок по другой причине —
переводишь затронутый агрегат на rich-модель в том же PR, если это укладывается в
бюджет ревью. Не укладывается — заводится задача, а не «когда-нибудь потом» в комментарии.

**Массовой миграции ради миграции не делаем.** Отдельный PR «сделаем Report богатым»
без продуктовой причины — не нужен.

## Последствия

- В репозитории надолго два стиля: анемичное легаси и rich-новьё. Это принято сознательно,
  граница проходит по времени написания, а не по модулю.
- Требование принуждается ревью и этим ADR, а не гейтом: автоматически отличить
  «богатую» модель от анемичной нечем. Ссылка на ADR-0003 в ревью — достаточное основание
  вернуть PR.
- Rich-домен — предпосылка для mutation testing (Stryker). До того как домен появится,
  мутационное тестирование смысла не имеет и в программу не входит.
- Инструкции агентам (`ROOT.md`, `AGENTS.md`, `CLAUDE.md`) обязаны вести сюда — иначе
  решение не доедет до исполнителя.

## Отброшенные альтернативы

- **Полный DDD по всем агрегатам сразу.** Дорого, риск переписать 39k строк ради формы,
  без сети безопасности из тестов — недопустимо.
- **Не делать DDD вообще, ограничиться правилами слоёв.** Дёшево и даёт эффект на дрейф,
  но новые фичи продолжают накапливать анемичную логику в сервисах.
- **Пилот на одном агрегате (`Report`) и решение по итогам.** Откладывает решение
  и оставляет остальной новый код без правила на всё время пилота.
