# ADR-0018: Контракт описывает работающий API — формы как есть, `required` про присутствие ключа

## Статус

Дата: 2026-07-26

Accepted.

Решение принял: владелец продукта.

Выделено из ADR-0005 без изменения смысла: правила описания провода и список
отступлений от канона перенесены сюда, чтобы ADR-0005 остался решением о contract-first.

## Контекст

По ADR-0005 `specs/contracts/<module>/openapi.yaml` — источник правды, а контроллеры
наследуют сгенерированные базы. Но yaml восстанавливался поверх API, которым уже
пользуется заказчик, а единственный клиент — фронтенд этого же монорепо. Любое
расхождение описания с проводом становится либо ломающим изменением, либо ложью в
контракте, из которой генераторы выводят неверные типы.

## Решение

**Контракт описывается с работающего API, а не наоборот.** Существующие URL, имена
query-параметров и формы ответов переносятся в yaml как есть, включая отступления от
канона (см. ниже). Приведение к канону — отдельная задача с правкой фронта, иначе
описание контракта превращается в ломающее изменение. Осознанные отклонения от снятой
формы фиксируются поимённо — см. ADR-0019 «Сужение wire-контракта reports».

### Пути, объявленные дважды

В модуле users каждая пользовательская ручка доступна и по короткому адресу
(`/v1/users/**`), и по адресу с контекстом
(`/v1/workspaces/{workspaceId}/teams/{teamId}/users/**`) — так исторически объявлены
маршруты контроллеров. Оба публичны, поэтому в контракте описаны оба: операции с
контекстом помечены суффиксом `InContext`, а контроллер реализует их делегированием.
Идентификаторы из пути там не используются — пользователь всегда берётся из identity.
Схлопнуть пару в один адрес можно только вместе с фронтом, отдельной задачей.

### Тип параметра пути — по факту связывания, а не по смыслу сегмента

Если действие до contract-first связывало сегмент (`[FromRoute] int workspaceId`), в
контракте он `integer`: мусор в нём отбивался как 400 и должен отбиваться дальше. Если
не связывало (сегмент был только в шаблоне маршрута), в контракте он `string` —
`WorkspaceIdIgnored`, `TeamIdIgnored`: раньше любой мусор доезжал до действия, и
типизация превратила бы это в 400, то есть в изменение публичного поведения. Внутри
одного модуля обе формы соседствуют: `GET .../teams/{teamId}/members` берёт команду из
пути (`integer`), а рабочее пространство — из identity (`string`).

### `required` — про присутствие ключа, `nullable` — про допустимость `null`

Это два независимых измерения, и смешивать их нельзя. MVC настроен только на snake_case
(`AddJsonOptions`), `DefaultIgnoreCondition` не задан, поэтому присутствующее
`null`-значение сериализуется, а не пропускается: в ответах ключ есть всегда, включая
`null`. `WhenWritingNull` включён только для SignalR (`PayloadSerializerOptions`) — на
HTTP-контракт это не распространяется.

Отсюда правило для схем **ответов**: каждое свойство обязано быть в `required`, а
законный `null` выражается отдельным `nullable: true`. Пропуск свойства в `required`
означал бы «ключа может не быть», чего API не делает, и генераторы выводили бы из этого
необязательное поле (`string?` в C#, `field?:` в TypeScript) там, где фронт знает ключ
обязательным.

Схемы **запросов** этому правилу не подчиняются: там отсутствие ключа — рабочая
семантика (PATCH «не трогать это поле», необязательный фильтр), и ужесточать их нельзя.
`ReportPatchRequest`, `BugRequest`, `BugPatchRequest`, `CommentRequest.audience` и
`ReportCountsScope` намеренно оставлены с неполным `required`.

Живой пример разницы — `receive`/`expect` у бага: они `NOT NULL` только в миграции 001,
миграция `009_report_team_organization.sql` снимает оба ограничения, а бизнес-правило
требует заполнить хотя бы одно поле, а не оба. Ключи присутствуют всегда, значение
любого из них может быть `null` — значит `required` **и** `nullable: true`.
Доказательная база — contract-снимки: сид `v2.reports.get` содержит баг только с
`receive` и баг только с `expect`, а `v2.bugs.patch.one-field` фиксирует, что PATCH
такого бага возвращает второй ключ как `null`.

Пустая коллекция и `null` в снимке формы неразличимы с «ключа нет», поэтому места, где
форма предъявляется только данными (вложения, ссылки, вложенные коллекции), сидируются в
contract-тестах явно.

## Последствия

- Описание контракта не меняет поведения: перегенерация даёт нулевой дифф, а снимки
  фиксируют провод до и после.
- Списки `required` в схемах ответов восстановлены по фактическим ответам и снимкам,
  поэтому вывод DTO фронта из yaml не даёт необязательных полей там, где ключ есть
  всегда. Это сняло блокер перевода фронта на сгенерированные типы (ADR-0005).
- Каждое отступление от канона остаётся видимым долгом с отдельной задачей, а не
  чинится молча по ходу описания.

### Отступления от канона AIP в описанном контракте

Список того, что описано «как есть» и требует отдельной задачи на приведение. Ни одно
из отступлений не чинится по ходу описания: у каждого на другом конце фронт.

> Строка про camelCase в query отменена ADR-0009: это не отступление, а принятая
> форма контракта. Форма `counts` изменена там же — `counts[].count` вместо
> значений свободного словаря.

| Отступление | Где | Почему не чиним здесь |
| --- | --- | --- |
| enum-like значения числами, не строками snake_case | `status`, `creator_type`, `audience`, `attach_type` | Числа лежат в БД и в коде фронта; смена — ломающее изменение обеих сторон |
| `long` наружу числом, не строкой | `total` в списке репортов, `counts.*` | То же: парсинг на фронте рассчитан на число |
| query-параметры в camelCase | `userId`, `teamId`, `reportStatuses`, `creatorTypes` | Имена в URL, по ним ходит фронт |
| create отвечает 200, а не 201 | `POST /v2/reports` | Контроллер возвращает модель напрямую; снимок контракта фиксирует 200. Superseded by [ADR-0011](0011-created-report-location.md) |
| ошибки не Problem Details | все `4xx` | Осознанное решение «Формат ошибки» в ADR-0005; Superseded by [ADR-0008](0008-problem-details.md) |
