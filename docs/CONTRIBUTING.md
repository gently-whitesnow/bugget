# Вклад в проект

Спасибо, что хотите помочь. Ничего согласовывать заранее не нужно — приносите PR.

## Процесс

1. Ветка, изменения, пул-реквест в `main`.
2. Все проверки зелёные: `./scripts/quality/verify.sh` — то же самое крутится на PR.
3. Ревью. Обязательного approval нет, мёрж блокирует только красный CI (контекст
   `ci-ok`), но PR смотрят глазами — дождитесь ответа.
4. Мёрж. Можно поставить «Merge when ready»: GitHub вольёт сам, как только CI позеленеет.
   На draft-PR автомёрж не ставится, при конфликте или красном CI снимается.

Ключевые изменения попадают в
[GitHub Releases](https://github.com/gently-whitesnow/bugget/releases) — это единственный
журнал изменений, отдельного CHANGELOG нет.

## Что проект берёт, а что нет

Миссия Bugget — **создавать процесс работы с багами, делая упор на удобство и
эффективность**. Это и есть фильтр: изменение принимается, если делает работу с багами
удобнее или быстрее.

Приносите не диффы, а интент: что в текущем процессе неудобно и как изменение это чинит.
Дальше можно включать effort посильнее — репозиторий сам расскажет, как в нём писать код.

Reuse-first: новый эндпоинт, схема в контракте, stored function, колонка или таблица —
последний вариант, а не первый.

## Дисциплина PR

Бюджет ревью — примерно **600 строк бизнес-логики на PR**. В бюджет **не входят**
сгенерированный код (`*.g.cs`, `frontend/src/shared/api/generated/*.d.ts`), тесты,
документация, DDL и миграции, форматирование и механические перемещения файлов.

Больше — режьте на слайсы и несите по очереди: крупная фича одним куском не ревьюится,
её либо принимают на веру, либо отклоняют целиком.

## Что должно быть в PR и в коммитах

Описание PR отвечает на вопрос «можно ли это влить»: что меняется, зачем, чего изменение
касается на проде (публичный контракт, схема БД, конфигурация, миграции) и как проверено.
Если из текста нельзя понять, почему изменение выглядит именно так, PR вернётся автору.

Тело каждого коммита — четыре блока. Пустой блок опускается, выдуманный хуже
отсутствующего.

```
<type>(<scope>): <краткая суть в повелительном наклонении>

Почему этот код появился:
- Что было не так до изменения. Симптом, а не пересказ диффа.

Решение:
- Что сделано и почему именно так.

Отброшено:
- Какие альтернативы рассматривались и чем они хуже.

Ограничения:
- Что осталось незакрытым, где проходит граница изменения, что сознательно не трогали.
```

Держать это в голове не нужно — в репозитории лежит шаблон
[`.gitmessage`](../.gitmessage), подключается один раз:

```sh
git config commit.template .gitmessage
```

Архитектурное решение, которое переживёт этот PR, живёт не в коммите, а в ADR
(`specs/ADR/`). Осознанное послабление гейта (`enabled: false`, задранный baseline,
новый `#pragma warning disable`) обосновывается в теле коммита — иначе гейт
`backend-suppressions` не пустит.

## Локальная разработка

Полный контур поднимается одной командой (см. [README](../README.md#быстрый-старт)):

```sh
cd deploy
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --env-file env/dev.env --profile full up --build
```

Проверки перед пул-реквестом:

```sh
./scripts/quality/verify.sh          # все гейты, это же крутится на PR
./scripts/quality/verify.sh --fast   # без медленных гейтов, не требует Docker
./scripts/quality/verify.sh --list   # что вообще проверяется
```

Набор гейтов лежит в `.quality/quality.config.json` — новая проверка добавляется туда,
а не в workflow. Подробности — в [README](../README.md#проверки-качества).
