# ADR-0008: RFC 9457 для HTTP-ошибок

- **Статус:** Accepted
- **Дата:** 2026-07-29

## Контекст

`ErrorResponse` с полями `error`, `reason` и `error_list` был самописным форматом.
Он расходился между Result-ветками, middleware и model-state, а универсальные клиенты
не распознавали его как ошибочный media type.

## Решение

HTTP-граница возвращает RFC 9457 `application/problem+json`. Единственный adapter
строит `type`, extension `code` и статус из одного дескриптора; `type` всегда равен
`urn:bugget:error:<code>`. Domain/Application продолжают передавать только свои
ошибки и не получают зависимость от ASP.NET `ProblemDetails`.

RFC-поля и вычисляемые `code`/`traceId` зарезервированы: прикладной словарь extensions
их не занимает, канонические значения фабрики всегда выигрывают. Иначе инвариант
«`type` и `code` из одного дескриптора» разваливался бы снаружи, одним аргументом вызова.

Model-state использует встроенный `ValidationProblemDetails`: словарь `errors` содержит
wire-имена полей тела запроса, которые отправляет клиент, и сообщения. Имя нормализуется
на каждом сегменте пути, включая вложенные объекты и элементы массивов (`scopes[0].key`),
и источником имён служит JSON-метаданные MVC, а не собственная таблица. Имена query- и
route-параметров сохраняют camelCase по ADR-0005; пути ошибок десериализации (`$.foo`)
приходят от System.Text.Json и не переписываются. Для 5xx detail не публикуется;
в ответ включается traceId для корреляции с журналом — он обязателен в контракте, потому
что adapter отдаёт его во всех ответах.

HTTP-adapter живёт в API-слое, а не в `Flow`: общий код знает только RFC-механику и
generic-дескрипторы. Каталоги прикладных ошибок принадлежат своим API-модулям; доменные
ошибки передают свой code/title и получают HTTP-статус в adapter-расширении.
`Bugget.Http` — временный узел, который растворится в `Bugget.Api` по ADR-0001; поэтому
рёбра `Users.Api → Bugget.Http` и `Authorization.Api → Bugget.Http` допустимы.
Два `ErrorExtensions` не объединяются: они работают с разными типами ошибок, а их слияние
принадлежит миграции ADR-0004.

## Периметр: ответы, которые собирает не контроллер

Ответ, у которого есть только статус, — тоже ответ контракта. Промах маршрутизации,
неподходящий метод и media type, отказ аутентификации (challenge) и авторизации
(`Forbid()`), пустые `NotFound()`/`Unauthorized()` из контроллеров закрываются одним
общим каталогом generic-дескрипторов (`CommonProblemDescriptors`) и одним местом записи —
`UseProblemStatusCodes`, обработчиком `UseStatusCodePages`. Он срабатывает только на
ответе без тела и Content-Type, поэтому уже собранный problem+json не трогает.

`IProblemDetailsService` в контуре не используется, и `AddProblemDetails()` снят: ответ
по правилам ASP.NET — это второй adapter с чужим `type` и без нашего `code`. По той же
причине включено `ApiBehaviorOptions.SuppressMapClientErrors`: собственное отображение
пустых 4xx в MVC давало третью форму ошибки. Незнакомый статус не остаётся
без кода — он получает выводимый `http_<status>`, потому что ответ без стабильного кода
клиенту разбирать нечем.

Единственное исключение — 401 внешнего nginx: он отвечает раньше приложения, лежит вне
монорепозитория и остаётся не-JSON. Парсер фронта эту форму обязан переживать.

Ошибка realtime-канала берёт тот же дескриптор, но не называется RFC 9457 и не имеет
Content-Type: в сокете нет ни статуса, ни `instance`, ни места под media type. Общее —
только каталог: `code` в `HubException` совпадает с тем, что клиент увидел бы в
problem+json на ту же ошибку. Свой каталог кодов SignalR не заводит.

Текст исключения не публикуется ни на одной границе. Middleware модуля authorization,
который отдавал `{ error: ex.Message }` на 404, переименован в `NotFoundExceptionMiddleware`
по факту своей работы и собирает тело общим адаптером.

## Последствия

Это намеренно ломающая замена старой wire-формы. Единый фронтенд монорепозитория уже
умеет читать обе формы, поэтому совместимый rollout возможен одним изменением.

## Статус прежнего решения

Часть ADR-0005, утверждавшая не-RFC формат ошибок, **Superseded by ADR-0008**. Остальные
решения ADR-0005 о contract-first и генерации остаются действующими.
