# ADR-0012: Enum-like значения публичного HTTP API — строки `snake_case`

- **Статус:** Accepted
- **Дата:** 2026-08-01
- **Решение принял:** владелец продукта

## Контекст

Публичный HTTP-контракт модуля reports отдавал и принимал enum-like значения числами:
`status` репорта и бага, `creator_type`, `audience`, `attach_type`. Число на проводе
не самоописательно — ни ответ в логе, ни тело в devtools не читаются без сверки с
кодом, — а описания в OpenAPI успели разойтись с реальностью: `Bug.status` в контракте
перечислял `1 fixed, 2 verified, 3 rejected`, тогда как домен, БД и фронт работали с
`1 verified, 2 rejected, 3 fixed`. Числовая форма такое расхождение не ловит: и то и
другое — `integer`.

У API один клиент — frontend этого же монорепозитория, поэтому смена формы значений
ломает ровно одну связку. Схему БД программа работ не меняет, а числовое представление
в домене и Postgres завязано на существующие записи.

Владелец подтвердил операционное условие: frontend и backend выпускаются и
откатываются одной согласованной парой образов, смешанные версии не являются
поддерживаемым состоянием.

## Решение

Enum-like значения публичного HTTP API модуля reports — закрытые множества строк
`snake_case`, объявленные схемами в `specs/contracts/reports/openapi.yaml`:

| Схема | Значения |
| --- | --- |
| `ReportStatus` | `backlog`, `resolved`, `fix`, `rejected`, `test` |
| `BugStatus` | `open`, `verified`, `rejected`, `fixed` |
| `CreatorType` | `user`, `system`, `tg_beta_tester` |
| `CommentAudience` | `internal`, `external` |
| `AttachType` | `fact`, `expected`, `comment`, `bug_step` |

Форма одна и на выходе, и во входных телах, и в query-фильтрах (`reportStatuses`,
`creatorTypes`, `attachType`, `statuses`, `creator_types`). Имена query-параметров не
меняются: их camelCase — часть публичного контракта (ADR-0005).

Домен, прикладной слой и Postgres остаются числовыми. Перевод живёт ровно на
HTTP-границе:

- `Bugget.Api/Mappers/WireEnumMapper.cs` — поимённое соответствие числа и значения
  контракта в обе стороны;
- `Bugget.Api/Http/WireEnum*.cs` — JSON-кодек, который пишет и читает строку из `enum`
  OpenAPI;
- `Bugget.Api/Binders/WireEnumModelBinderProvider.cs` — тот же строгий разбор для query.

Переключение атомарное: transitional `oneOf`, приём чисел на входе, переключатель
формата ответа и отдельный cleanup-PR не вводятся. Операционная гарантия —
одновременная выкладка и совместный откат пары образов; порядок и сам runbook в эту
задачу не входят.

`ADR-0005` этим решением не отменяется: contract-first и запрет ручной правки `*.g.cs`
остаются в силе, меняется только форма значений внутри контракта. `ADR-0007` не
затрагивается — SignalR остаётся числовым, и перевод числа события в значение провода
делает явный адаптер фронта (`entities/report/lib/socketEnums.ts`).

## Последствия

- Тело ответа и фильтры читаются без сверки с кодом; неверное описание `Bug.status`
  в контракте исправлено вместе с переходом.
- Неизвестная строка на входе — 400 (validation problem), одинаково для тела и query.
  Разбор строгий: ни другой регистр, ни имя CLR-члена, ни число старого провода
  значением не считаются.
- Неизвестное число на выходе — отказ, а не «ближайшее» значение: расхождение
  хранилища с контрактом не маскируется чужим статусом в карточке.
- `null` и отсутствие optional-полей сохраняют прежний смысл «не трогать».
- Генератор NSwag называет члены enum по своим правилам (`tg_beta_tester` →
  `Tg_beta_tester`) и вешает на свойства конвертер, пишущий имя CLR-члена. Поэтому
  строка провода берётся из `EnumMemberAttribute`, а не из имени, и это принуждается
  тестом, а не соглашением.
- На фронте значения enum'ов — `as const`-объекты, чей тип берётся из сгенерированного
  контракта: пропавшее в yaml значение ломает сборку, а не расходится с сервером молча.
- В константы фронта добавлен `tg_beta_tester`, которого там не было: внешний автор
  больше не разрешается как внутренний пользователь.
- Смешанные версии frontend/backend несовместимы по построению. Это принятый риск
  ручного нарушения порядка выкладки, а не недосмотр.

## Отброшенные альтернативы

- **Поэтапная совместимость** (числа на входе + переключатель формата ответа +
  cleanup-PR). Убирает окно несовместимости при независимой выкладке, но владелец
  гарантировал атомарную пару образов, а временная толерантность оставляет в коде
  две формы одного значения и требует отдельного гейта на её снятие.
- **Новая версия `/v3`.** Постоянное дублирование публичного API ради единственного
  клиента.
- **Параллельные поля (`status_name` рядом с `status`).** Два источника правды в
  каждой вложенной форме.
- **Сохранить числа и починить только описания.** Оставляет провод нечитаемым и не
  ловит следующее расхождение описания со значением.
