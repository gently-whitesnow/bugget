# ADR-0014: Доступ агента — personal access tokens и in-process MCP

- **Статус:** Accepted
- **Дата:** 2026-08-07
- **Решение принял:** владелец продукта (эпик «Bugget MCP MVP», kaiten 236887)

## Контекст

Тестировщики заводят баги в bugget, а чинят их разработчики руками. Цель эпика —
дать AI-агенту (Claude Code и подобным) прочитать баг и отчитаться о починке без
разработчика в цепочке. К старту эпика в продукте не существовало ни одного
неинтерактивного входа (единственный — dev-only fake-login), а весь API имел
ровно одного клиента — фронт этого же монорепозитория (ROOT.md).

Существовавшие опоры, на которых построено решение:

- `/_internal/auth` — единственная точка настоящей проверки identity: nginx зовёт
  её `auth_request`-сабреквестом и переносит ответные `Auth-Request-*` заголовки
  в реальный запрос; сам API внутри модуля reports доверяет заголовкам
  (header-trust) без криптопроверки.
- `CreatorType` (User/System/TgBetaTester) уже различал нечеловеческих акторов в
  комментариях, багах и доменных событиях (`ActorCreatorType`).
- SignalR-хаб `ReportPageHub` — прецедент не-REST транспорта в том же процессе и
  том же nginx location, что и контроллеры.
- `IReportPatchPostAction`/Mattermost — прецедент «после действия дёрнуть внешнюю
  систему» с глобальной env-конфигурацией и no-op по умолчанию.

## Решение

Дать агенту вход через personal access token и MCP-эндпоинт внутри процесса
`bugget-api`, ничего не меняя в nginx и в модели доверия.

Составные части одного решения:

1. **PAT** (`bgt_pat_…`, 32 случайных байта): в БД — только SHA-256 без соли и
   KDF (секрет высокоэнтропийный, перебирать нечего, сверка — на каждом запросе);
   значение показывается один раз при выпуске. Токен привязан к одной паре
   workspace+team и строго личный: admin-доступа к чужим токенам нет. Срок по
   умолчанию 90 дней; бессрочный через публичный API невозможен. Выпуск, список
   и отзыв — self-service в Settings.

2. **Аутентификация**: PAT — вторая схема рядом с JWT; policy-схема
   `/_internal/auth` выбирает по формату Bearer. На успехе уходят те же
   `Auth-Request-*` заголовки плюс `Auth-Request-Auth-Method` — способ входа.
   Workspace/team из URL обязаны совпадать со scope токена (fail-closed 401 на
   путях без обоих сегментов). Header-trust ниже по цепочке не изменился.

3. **Атрибуция**: действие, пришедшее по PAT, пишется в историю как
   `CreatorType.Agent` — выводится из claim `auth_method` в
   `UserIdentity.ActorCreatorType`, сервисы штампуют его без участия
   MCP/REST-слоёв. Отдельной сущности «агент» нет: владелец записи — человек,
   выпустивший токен, способ входа — признак агентности.

4. **MCP in-process**: официальный SDK (`ModelContextProtocol.AspNetCore`),
   Streamable HTTP на `/v1/mcp` в том же `UseEndpoints`, что и хаб, под той же
   policy header-trust, тем же nginx location — без правок nginx. Инструменты —
   тонкие адаптеры над интерфейсами `Bugget.Application` (как контроллеры), под
   теми же арх-правилами сборки Api; их точный список закреплён contract-тестом:
   10 инструментов — read (`list_reports`, `get_report`, `search_reports`,
   `get_attachment`) и write (`create_report`, `create_bug`, `patch_report` —
   принимает только статус, `patch_bug`, `create_comment`, `update_comment`).
   Создание репорта и бага (kaiten 237700) добавлено после MVP: чтобы найденный
   баг заводился тем же PAT, а не выходом в неавторизованный CLI скилла. Валидация
   длин REST повторена в инструментах явно: DataAnnotations без MVC-биндинга не
   срабатывают.

   Ответственного `patch_report` не принимает, но при смене статуса агентом его
   подставляет сервер (kaiten 238350): `fix` — владелец токена, `test` — тот, кто
   вёл репорт до правок, иначе автор. Агент не пользователь и ответственным быть
   не может, а id людей ему неоткуда знать — поэтому правило живёт в домене
   (`AgentReportHandoff`), а не в описании инструмента.

5. **Wire MCP не описывается в `specs/contracts/`**: это не фронтовый
   HTTP-контракт (ADR-0005 остаётся про REST), форму задаёт спецификация MCP и
   атрибуты SDK. Строки enum'ов — те же, что у REST (общая карта ADR-0013).
   PAT-ручки (выпуск/список/отзыв) — обычный contract-first: их зовёт фронт.

6. **Token-economy вложений** зашита на сервере, а не оставлена клиенту:
   картинки — превью по умолчанию, оригинал только по явному флагу; видео —
   байты не уходят никогда (кадр-превью + внешний `download_path` для человека);
   текст — как есть, без перекодировок и `\uXXXX`, страницами с явными
   `total_chars`/`truncated`.

## Последствия

- Появился неинтерактивный вход. Цена утечки токена ограничена scope (одна
  команда), сроком (90 дней по умолчанию) и отзывом; в хранилище секрета нет.
- «Ровно один клиент API» из ROOT.md уточняется: у REST-контракта клиент
  по-прежнему один — фронт; MCP — отдельная поверхность с собственным контрактом
  и своим потребителем (агент). Право менять REST по-прежнему держат гейты
  contract-first.
- Действия агента отличимы в истории от действий человека (бейдж «агент» в UI,
  `actor_creator_type` в domain_events) — это держат contract-тесты, а не ревью.
- Принуждение: арх-правила сборки Api накрывают MCP-слой (доказано красной
  фикстурой `LeakingMcpTool`); точный список инструментов, изоляция workspace на
  чтение и запись, «значение токена существует только в ответе на выпуск»,
  «default-путь не отдаёт оригиналов», атрибуция агента — всё закреплено
  contract-тестами в `Bugget.IntegrationTests/Contract/`.

## Вне MVP (сознательно не сделано)

- CRUD шагов, report-links, аналитика, workspace/team/settings через MCP.
  (Создание репортов и багов было здесь на старте эпика; вынесено в инструменты
  по kaiten 237700 — см. п. 4.)
- Отдельная агент-сущность (service user): отброшена в пользу атрибуции по
  способу входа (kaiten 236888) — вернуться, только если понадобится агент со
  своей идентичностью.
- Патч участников репорта: его нет и в REST.
- OCR, перевод, транскрипция и байты видео для модели.
- Автозапуск агента по новым багам (поллинг/вебхук на создание).
- Rate-limiting PAT-аутентификации и write-инструментов; ротация и лимит числа
  токенов.

## Отброшенные альтернативы

- **Service user + `UserType`:** новая сущность, admin-флоу создания и вопросы
  «сколько на команду» не нужны, пока агент работает от имени человека;
  атрибуция по `auth_method` даёт то же различение одной строкой enum.
- **Валидация PAT в nginx:** размазала бы логику auth по двум местам; сегодня
  nginx делегирует всё `/_internal/auth`, PAT встал туда же.
- **Отдельный MCP-сервис или top-level путь `/api/mcp`:** второй процесс или
  новый nginx location против «в том же location, та же policy, ноль правок
  nginx»; заодно scope-проверка PAT по URL работает как есть.
- **bcrypt/argon2 для хэша токена:** KDF защищает низкоэнтропийные пароли; здесь
  секрет случайный, а сверка нужна на каждом запросе.
- **Placeholder-инструмент ради tools capability:** пустая `ToolCollection`
  включает capability без фейкового инструмента, который пришлось бы вычищать.
- **Описание MCP-инструментов в `specs/contracts/**`:** из этого yaml ничего не
  генерировалось бы — форму держит SDK; расхождение стало бы третьим источником
  правды.
